Fondation · décidé

Une coquille : chat, dashboard, nav.

Thomas accompagne une exploitation végétale, quelle que soit sa filière. L’agriculteur parle dans le chat. La barre partagée bascule vers le dashboard pour approfondir. La navigation collapsible mène aux registres — Planification et Calendrier inclus, même outil.

Méthode produit · décidé

Cahier d’abord, recode ensuite. Les outils existants (Thomas Desktop V2, Basile Pro, mobile V2) nourrissent le cahier : périmètre métier, écrans utiles, frictions. Ils ne dictent ni l’architecture, ni les composants, ni les parcours V3.

Une seule logique produit et un seul style Thomas V3, chat + registres. Porter Basile « dans » Thomas, ou Desktop « à côté » avec une autre peau.

Optimiser, simplifier, rendre plus agréable que V2 / Basile. Reproduire feature-par-feature sans triage.

Plan / carte de la ferme · décidé

Le registre Plan de la ferme est une carte interactive (satellite / ortho) pour dessiner, ajouter et modifier les formes des parcelles, et pour modifier la ferme elle-même (fiche + emprise). Même coquille. Ordi = dessin et édition fine ; téléphone = consultation, sélection, ouverture des fiches. Cahier détaillé : Carte de la ferme (flux dessin, ajout, édition, fiche ferme, données, scénarios agent, C1–C6).

Ajouter une forme À la fermeture : panneau « Nouvelle parcelle » (nom, type) → écrit plots + geometry ; ou « Lier à une parcelle existante ». On peut aussi partir de la liste Parcelles → « Dessiner sur la carte ».

Registres

Chaque entrée suit trois gestes. La vue d’ensemble compte, cherche et filtre, puis liste les fiches. Toucher une fiche ouvre le formulaire rempli. Le bouton plus ouvre le formulaire vide. Le chat peut ouvrir ce formulaire déjà rempli. Écrans Figma : « 03 Ferme & ressources » (carte + menus) et coquille « 00 ».

Le nom est exigé pour une parcelle. Désactiver une parcelle la garde dans l’historique. Le calendrier, les observations, les traitements, les ventes et le personnel suivent la vue personne. Les parcelles, le plan / carte, la planification, le matériel, les prix et les conversions restent ceux de la ferme.

Harness

Le code orchestre. Jev juge. Le LLM dialogue. Les prompts ne choisissent plus l’outil par une chaîne de textes libres. Chaque moteur a un rôle fixe.
La lecture est directe. L’écriture complète s’enregistre. Si la carte est complète et sans ambiguïté, Thomas écrit tout de suite. Sinon il attend une précision, une répartition, ou une confirmation. Une tâche déjà enregistrée peut être supprimée depuis le chat.
Les droits de l’exploitation s’appliquent à chaque outil. Ni Jev ni le LLM ne contournent les accès des membres. Les données sont celles de la ferme. La visibilité se restreint ensuite.
Une compétence de conseil est un contenu versionné. Elle appartient à un groupe, cite ses sources et n’ajoute pas un second moteur. Cette partie n’est pas construite dans le premier lot.

Jev et LLM · décidé

Thomas V3 n’est pas un agent LLM unique. Ce n’est pas non plus Jev seul. C’est un mixte, avec le code au centre. Le bench scripts/jev-bench a déjà montré que Jev route et extrait mieux, moins cher, sur les cas typés. Le LLM reste nécessaire dès qu’il faut parler, reformuler ou trancher un cas ambigu.

MoteurRôleExemples
Code Contrôle le parcours. Charge le contexte. Compose les réponses. Appelle les outils. Pose les cartes. Applique les seuils de confiance. Découper un message en intentions déjà détectées. Recopier la serre sur deux cartes. Écrire tasks après confirmation. Refuser un accès hors vue.
Jev (TypeSafe System One) Jugements typés, rapides, à probabilités. Détecte les éléments et choisit parmi des options connues. Ne génère pas de prose. Usage : tâche faite, prévue, observation, vente, réglage, aide, conversation, précision. Champs : culture, action, durée, parcelle, sous-parcelle, personne, fait ou prévu. Plusieurs questions atomiques en parallèle sur le même état.
LLM Dialogue et formulation. Intervient quand le texte libre compte, ou quand Jev est peu confiant. Demande de précision sous une carte. Réponse de conversation. Reformulation d’une lecture (météo, ePhy, temps au m²). Escalade d’un message trop mélangé ou trop vague.

Pourquoi pas un seul LLM

Un fournisseur LLM unique simplifie l’architecture, mais repart sur la dette V2 : classification floue, extraction fragile, coût élevé à chaque message, et prompts qui tentent de tout faire. Jev est fait pour les décisions bornées que le chat pose en boucle : quelle intention, quelle culture, quelle parcelle parmi celles de la ferme. Le LLM seul reste meilleur pour rédiger une question ou une réponse.

Pourquoi le mixte tient malgré la complexité

La complexité n’est pas « deux modèles qui se parlent ». C’est le code qui enchaîne des étapes courtes. Jev ne reçoit jamais toute la ferme. Le code construit un état mince : le message, les candidats utiles (parcelles, cultures ouvertes, membres, matériels), et les options du choix. Chaque question Jev pointe vers ce qu’il doit juger. Le LLM, lui, reçoit l’historique de conversation et le résultat déjà structuré, pas une seconde copie brute de toute la base.

RisqueRègle
Contexte trop gros dans JevÉtat par intention. Candidats filtrés par la ferme et la vue. Pas de dump de tables.
Deux moteurs qui se contredisentJev propose des champs typés. Le LLM ne réécrit pas ces champs. Il formule la question ou la réponse autour.
Orchestration opaqueLe parcours est dans le code, visible et testable. Jev et le LLM sont des appels, pas des agents libres.
Cas douteuxSous le seuil de confiance, le code escalade au LLM ou pose une précision. Il n’écrit pas.

Parcours d’un message

  1. Le code charge le contexte utile de la ferme pour la vue en cours.
  2. Jev route : une ou plusieurs intentions, avec probabilités.
  3. Pour chaque intention d’écriture, Jev extrait les champs parmi les candidats. Le code assemble la carte.
  4. Si un champ manque ou si la confiance est basse, le LLM formule la demande sous la carte. Les autres cartes restent confirmables.
  5. Si l’intention est une lecture ou une conversation, le LLM rédige la réponse à partir des faits déjà lus par le code.
  6. La confirmation de l’agriculteur déclenche l’outil. Ni Jev ni le LLM n’écrivent seuls en base.

Système de mémoire · décidé

La mémoire de Thomas n’est pas un seul store RAG. Six couches, rôles distincts. Aligné sur l’état mince déjà décrit pour Jev.

CoucheContenuDurée / vérité
État ferme mince (DB structurée) Parcelles, plans ouverts, membres, matériels, prix, cultures en cours — candidats filtrés pour la vue Source de vérité opérationnelle. Pas de dump de tables dans le prompt.
Fil courant Historique de la conversation ouverte + cartes confirmées de la session Contexte immédiat du dialogue. Pas une nav « historique chat » dense.
Mémoire épisodique Résumés versionnés des conversations passées, recherchables Pour retrouver « ce qu’on a dit en mars », pas pour rejouer tout le fil brut.
Mémoire métier structurée ITK, itinéraires, séries / plans, coûts culture — entités (voir Itinéraires) Vérité métier versionnable. Pas du RAG flou seul.
Faits confirmés Écritures après confirmation utilisateur (cartes) — tâches, observations, ventes… Seules lignes opérationnelles durables issues du chat.
Cache outils Résultats d’appels récents (ePhy, conversions, lectures) Court, non durable. Invalidable. Jamais source de vérité seule.
Conséquence harness. Jev reçoit l’état mince + candidats. Le LLM reçoit le fil courant et les faits déjà structurés. Les résumés épisodiques et l’ITK structurés sont chargés à la demande par le code (outil / lecture), pas collés en masse à chaque message.

Plan de tests · place de Jev et fournisseur LLM · brouillon

La répartition Jev / LLM se tranche par mesures, pas par préférence. Le banc existant scripts/jev-bench sert de base : goldset, routage, extraction, orchestration, comparaison coût / latence / exactitude. On l’étend pour faire tourner les mêmes cas sur plusieurs moteurs et modèles.

TraitementRôle testéModèles

Côté OpenAI, on commence par les plus petits et les moins chers disponibles via API (ex. famille mini / nano), pas par un modèle frontier. Côté Mistral et DeepSeek, même logique : le plus petit qui tient le JSON structuré et le français agricole. Un quatrième fournisseur n’entre que s’il bat clairement le trio sur coût ou qualité de précision.

Jeux de cas

  1. Routage (O-…) — usage : tâche faite, prévue, observation, vente, réglage, aide, conversation, précision.
  2. Extraction (T-01 et goldset) — culture, action, durée, parcelle, sous-parcelle, fait/prévu, multi-activités.
  3. Précision — message incomplet ; juger si la question posée sous la carte est juste, courte, et ne bloque pas les autres cartes.
  4. Dialogue / lecture — météo, ePhy, temps au m² : réponse lisible à partir de faits fournis par le code, sans inventer.
  5. Stress contexte — même message avec état mince (candidats filtrés) vs état trop large, pour mesurer la dégradation de Jev et du LLM.

Critères de choix

Exactitude d’abord sur le typé. Un LLM moins cher qui se trompe de parcelle ou d’usage ne remplace pas Jev. Jev garde l’étape s’il gagne ou égale le meilleur LLM à coût et latence inférieurs.
Le LLM gagne sur la prose. Entre OpenAI mini, Mistral et DeepSeek, on retient celui qui pose les meilleures précisions et lectures, à budget et latence acceptables sur mobile.
Le mixte gagne s’il baisse le coût sans baisser l’exactitude. Sinon on simplifie : Jev partout où il suffit, un seul LLM pour le reste.
Un fournisseur LLM principal au premier lot. Le secours (autre API) n’est ajouté que si le bench montre un écart net sur un sous-jeu (ex. français libre, JSON cassé).

Livrable du bench

Un rapport par traitement : exactitude par champ, taux d’escalade, coût moyen par message, latence, exemples d’erreurs. À partir de ce rapport on fige : étapes Jev, étapes LLM, modèle retenu, seuils. Tant que le rapport n’existe pas, le fournisseur LLM et les seuils restent ouverts.

A1 · Multi-intentions. Tranché par le bench (qualité, vitesse, coût) : Jev découpe, ou LLM découpe puis Jev extrait.
A2 · Seuils. Calibrés sur le bench. Objectif : ~90 % de réussite sur le goldset typé.
A3 · LLM prose. OpenAI mini, Mistral, DeepSeek — choix par le bench. Détail du plan et du bot UI dans Tests.

Orchestrateur

L’orchestrateur est le code. Il lit le message, appelle Jev, puis le LLM si besoin, avant d’appeler un outil. Chaque intention devient sa propre carte, avec son propre outil. Une phrase qui mélange plusieurs travaux ne produit jamais une seule ligne.

Plusieurs activités. « J’ai désherbé une heure et récolté une demi-heure » donne deux cartes. La durée, la culture et le lieu propres à chacune restent sur leur carte. Ce qui est dit une seule fois pour l’ensemble, comme la date, la personne ou la parcelle, est recopié sur chaque carte et annoncé.
Fait ou prévu. Un travail déjà accompli, au passé ou au présent, prépare une tâche à enregistrer, tasks.status = terminee. Un travail à venir, « demain », « je vais », « il faut », « prévoir », prépare une tâche à planifier, tasks.status = en_attente, datée du jour dit. Les deux peuvent tenir dans le même message. Thomas le dit, et range chacune dans son statut.
Une demande sous sa carte. Si une intention manque d’une information, la question est placée sous la carte concernée. Les autres cartes restent confirmables, ensemble ou séparément.

Intentions

Une intention est soit une lecture, soit une écriture. La lecture répond tout de suite. L’écriture propose une carte et attend la confirmation. Un même message peut contenir les deux.

Les autres intentions s’appuient sur des tables déjà là : tâches, plans, ePhy, factures, observations, semences en stock. Les parcours chat se spécifient dans ce cahier (fondation + domaines) ; le fichier Figma actuel est à archiver puis reconstruire après stabilisation du CDC (pas de nouvelles pages Figma « Harness / Intentions » pour l’instant).

Visibilité

Les données vivent dans la ferme. En V2, un membre actif voit les tâches de toute la ferme. La V3 garde ce partage, puis le filtre. Trois vues : les siennes, celles de tout le monde, ou celles d’une personne.

VueQui peut l’ouvrirCe qui s’affiche
SoiChaque membreLes tâches, observations et temps dont il est l’auteur, ou un participant.
Toute la fermeChaque membre, sauf s’il est restreint à soiLes mêmes données pour tous les membres actifs.
Une personneLe responsable et le propriétaireLes données de ce membre, comme s’il les consultait lui-même.

Parcelles, sous-parcelles, plans, matériel, prix, conversions, itinéraires, météo et ePhy restent visibles pour la ferme. Ils ne portent pas de personne. Une restriction ne les cache pas.

Thomas applique la même vue dans le chat. « Mon temps sur les tomates » reste sur l’auteur. « Le temps de Marie » n’est répondu qu’au responsable ou au propriétaire. Un membre restreint à soi reçoit ses propres lignes, et Thomas le dit.

La filière ne crée pas un produit séparé. Elle change les libellés, les unités, la durée du cycle et les exemples.

Filières · décidé

Une seule UI / UX pour toutes les filières. Pas de skins, menus ou parcours distincts par filière. Les libellés, unités, durées de cycle et exemples s’adaptent ; la coquille, le chat, les cartes et les registres restent les mêmes. Un finetuning filière (modèles, catalogues, prompts) pourra venir plus tard — ce n’est pas une variante d’interface.

La V2 range déjà les cultures en maraîchage, pépinière, floriculture, arboriculture, grande culture et tropical. La V3 ajoute explicitement la viticulture et les plantes à parfum, aromatiques et médicinales. Une exploitation peut en combiner plusieurs.
