Événements d’erreur · décidé

Catalogue d’événements. Une sortie claire par situation.

On ne parle pas d’« erreur générique ». Chaque situation a un événement nommé, un comportement produit, et un parcours de normalisation / récupération. Le code émet l’événement ; le chat ou l’UI le traduit sans jargon technique pour le producteur.

Règles transverses. (1) Jamais d’écriture structurée silencieuse après un échec partiel. (2) Message utilisateur = une phrase + une action. (3) L’état peut rester en brouillon (carte non confirmée, fichier en quarantaine) sans corrompre la DB. (4) Logs techniques ≠ UI producteur.

Les surfaces qui affichent ces états (coquille, chat, registres, carte) : Navigation & chrome.

Parcours de sortie (patron)

  1. Émettre l’événement nommé (code + log).
  2. Afficher le message producteur + une action primaire (réessayer, choisir, corriger, annuler).
  3. Préserver ou isoler l’état (brouillon carte, file hors ligne, quarantaine fichier).
  4. Interdire l’écriture structurée jusqu’à résolution, sauf règles explicites (ex. confirmation partielle T-01).
  5. Après succès : effacer l’état d’erreur ; éventuellement journaliser la récupération pour les tests.

Tests

Chaque événement du catalogue a au moins un cas dans Tests (script déterministe et/ou bot UI). Le goldset agent doit couvrir AGT_* et VAL_* les plus fréquents.

Ouvert

Brouillon technique. Noms d’événements figés produit ; mapping exact codes HTTP / Supabase reste d’implémentation. Seuils timeout et durée de quarantaine fichiers à calibrer.
